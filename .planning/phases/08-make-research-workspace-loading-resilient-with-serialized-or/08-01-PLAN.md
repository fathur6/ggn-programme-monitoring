<interfaces>
Existing server contracts to preserve:
- `ensureResearchSheets_()` creates the eight research sheets and returns a sheet registry; it must publish the registry only after successful initialization.
- `seedResearchReferences_(sheets)` appends missing reference rows without clearing inactive/custom rows.
- `withResearchLock_(work)` is the compatibility entry point used by research writes and read projections.
- `ensureAssessmentSheets_()` initializes assessment sheets and definitions; assessment save/reset release the lock before their canonical post-save read.
- `freshResearchMappings_()` currently normalizes persisted TF rows during selected reads; this plan does not silently remove that brownfield response behavior.

Phase 8 preparation contracts to create and use:
- `withPreparedResearchContext_(programmeIdOrMqaCode, reader)` resolves the canonical research programme, acquires the shared lock once, invokes no-lock setup/migration/reference preparation, and passes a captured context to `reader`; aggregate readers project after capture, while compatibility readers keep any existing read-repair write inside this same owned boundary.
- `ensureResearchSheetsNoLock_(spreadsheet)` and `migrateLegacyResearchRowsNoLock_(programme, key, sheets)` assume the caller already owns the lock; `researchContext_()` must not append or migrate outside `withPreparedResearchContext_()`.
- `getResearchReferencesNoLock_(sheets)` reads/normalizes prepared reference rows without acquiring a lock. The public `getResearchReferences_()` may own a lock only when called outside a prepared boundary.
- Assessment setup has the same split (`ensureAssessmentSheetsNoLock_()` plus prepared definition/reference readers) so an assessment aggregate cannot reacquire the script lock through `ensureAssessmentSheets_()` or `getResearchReferences_()`.
</interfaces>

Resolved Phase 8 policy: use one named policy with a 5,000 ms per-attempt `tryLock` timeout, at most four acquisition attempts, and capped delays of 250/500/1000 ms only between the first three failed attempts. The nominal maximum is 21,750 ms; no call site may add another retry loop. No new package is needed; use existing Apps Script services and Node built-ins only.
</context>
